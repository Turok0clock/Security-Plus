P|Architecture allocates responsibilities and failure boundaries. With Infrastructure as a Service, a provider supplies infrastructure while the customer normally manages guest operating systems and applications. Platform as a Service reduces runtime management; Software as a Service provides the application. In every model the customer still has responsibilities such as identity, permissions, data decisions, and configuration. Exact contractual boundaries override slogans.
P|Hybrid cloud connects private and public environments and can create inconsistent identity, network, logging, and data policies. A responsibility matrix assigns duties; it does not enforce them. Containers share a host kernel, while virtual machines have separate guest operating systems. Microservices divide an application into interacting services; serverless delegates server operations but still requires secure code and permissions. Industrial systems prioritize safe reliable processes, so patching and scanning must account for operational constraints.
F|Locate the workload|Assign responsibilities|Identify isolation boundaries|Trace dependencies|Plan security and failure behavior
T|IaaS|Infrastructure as a Service provides compute, network, and storage resources. Customers commonly patch guest operating systems and secure their applications; providers protect underlying physical infrastructure.
T|PaaS|Platform as a Service supplies a managed runtime or application platform. Customers focus on application code, data, and configuration while the provider manages more of the operating environment.
T|SaaS|Software as a Service delivers a managed application. Customers still manage users, access, data sharing, and tenant settings rather than assuming the provider handles every security decision.
T|Shared responsibility matrix|Assigns security duties between provider, customer, and other parties for the specific service. It clarifies ownership and should be checked against contracts and service documentation.
T|Infrastructure as code|Uses machine-readable definitions to provision infrastructure repeatably. Review, versioning, testing, and secret handling are essential because mistakes can be replicated widely.
T|Microservices|Divides application capabilities into separately deployable services communicating through interfaces. It can improve independent scaling but adds service identity, network, and dependency complexity.
T|Containerization|Packages an application and dependencies in isolated processes that generally share a host kernel. Images, runtime privileges, and host security remain important; containers are not separate physical machines.
T|Serverless|Runs functions or managed workloads while a provider handles server provisioning. Customers still secure code, invocation permissions, dependencies, and data access.
T|Air gap|Physical separation removes direct network connectivity between environments. Removable media, maintenance devices, and people can still bridge the gap, so process controls remain necessary.
T|ICS / SCADA|Industrial Control Systems and Supervisory Control and Data Acquisition monitor or control physical processes. Safety, availability, long device lifetimes, and controlled maintenance constrain conventional IT changes.
T|Hybrid cloud|Combines distinct private and public cloud environments. Connectivity alone does not harmonize controls; mismatched access, logging, and network policies must be reconciled.
T|Embedded / RTOS|Embedded systems perform specific functions; a Real-Time Operating System emphasizes predictable response deadlines. Timing and safety constraints may matter more than desktop-style feature flexibility.
E|A company moves its application to IaaS but leaves its guest operating system unpatched because the provider owns the building. Physical hosting responsibility does not transfer guest patching. If a second application uses SaaS, the customer may not patch its servers but still must remove departed employees and control shared documents. Identify the service boundary before assigning responsibility.

P|Choose controls by placement and traffic path. An Intrusion Detection System observes and alerts; an Intrusion Prevention System in the traffic path can block. A Web Application Firewall interprets web requests, while a conventional packet filter may only evaluate addresses and ports. A forward proxy represents clients; a reverse proxy represents servers. A jump server mediates administration rather than ordinary browsing.
P|Network Access Control checks who or what can connect and may use 802.1X port-based authentication. Enterprise wireless can use 802.1X with centralized authentication; WPA3 describes wireless protection capabilities and does not alone specify corporate username authentication. Secure Access Service Edge combines distributed connectivity and cloud-delivered security for users and sites. Zero trust is an access model, not a substitute name for that delivered network service.

T|WAF|Web Application Firewall inspects application-layer web traffic and can block malicious requests. It complements secure coding and cannot repair every business-logic flaw.
T|IPS|Intrusion Prevention System inspects traffic inline and can discard or reject matched attacks. Placement and visibility determine what it can prevent; encrypted payloads may require supported inspection.
T|IDS|Intrusion Detection System observes suspicious traffic and alerts without itself being the inline blocking point. Detection can initiate a separate response workflow.
T|NAC|Network Access Control applies admission policy based on identity and device posture. It may restrict noncompliant endpoints to remediation access rather than immediately giving full network access.
T|Jump server|A controlled intermediary for administrative connections into protected systems. It centralizes access paths and logging but must itself be strongly secured.
T|Screened subnet|A separated zone for exposed services between trusted and untrusted networks. Rules limit access from the zone to internal resources; placement alone is not enough.
T|Forward proxy|Makes requests on behalf of clients, enabling outbound filtering, logging, or caching. It represents the user side of the connection.
T|Reverse proxy|Receives client requests on behalf of backend servers and can terminate connections or distribute requests. It represents the service side, unlike a forward proxy for users.
T|Fail-closed|Denies access when a security component fails. It favors blocking unauthorized access but can harm availability, so safety and business requirements must be considered.
T|Fail-open|Allows access or traffic when a component fails. It favors continuity but can remove a security barrier during the failure.
T|802.1X|Port-based network access control uses a supplicant, authenticator, and authentication server. EAP means Extensible Authentication Protocol and carries authentication methods; enterprise Wi-Fi often uses this framework with RADIUS.
T|SASE|Secure Access Service Edge combines wide-area connectivity with cloud-delivered security capabilities for users and sites. It can place consistent access controls near mobile users and cloud applications.

At headquarters, 802.1X admits a laptop to the network after authentication. A WAF separately protects the application's requests. These components act at different points; match the requested task to its point in the path.

P|Data state describes what is happening to the bytes: stored is at rest, moving across a connection is in transit, and actively processed is in use. A database can contain encrypted data at rest but decrypt selected values in memory for calculations. The word database does not determine state; follow the specific action. TLS protects a connection, not necessarily the stored file or the memory of an endpoint.
P|Data classification expresses sensitivity and handling requirements. Regulated data is subject to applicable obligations; public data is intended for open disclosure. Obfuscation makes interpretation harder but does not define a legal classification. Tokenization replaces values with references and protects the mapping separately. Masking changes what is displayed. Encryption transforms content under a key. A hash supports integrity comparison, not confidentiality or a clean-malware guarantee.
F|Identify the data and owner|Determine classification and obligations|Determine its current state|Choose protection for that state|Verify access and retention
T|Data at rest|Data stored on media such as disks, backups, or cloud storage. Protect it with appropriate access controls, encryption, key management, and disposal procedures.
T|Data in transit|Data moving between systems over a communication path. Authenticated encrypted protocols protect against interception and modification while crossing that path.
T|Data in use|Data actively processed in memory or by an application. Disk encryption alone does not protect plaintext after a legitimate process decrypts it for use.
T|Tokenization|Replaces sensitive data with a substitute token whose mapping is held separately. A token is not necessarily a mathematical encryption of the original value.
T|Masking|Conceals portions of displayed or copied data, such as showing only the last four digits. Verify that underlying storage and privileged access are also protected.
T|DLP|Data Loss Prevention inspects or controls sensitive-data movement according to policy. It may alert or block at endpoints, networks, or services and needs tuning to avoid disruptive false matches.
T|Data minimization|Collects and retains only data needed for a defined purpose. Less unnecessary data reduces exposure and handling burden without relying solely on stronger access controls.
T|Classification|Assigns sensitivity or handling labels based on impact and obligations. Owners and policy guide labels; the presence of encryption alone does not determine the classification.
T|Data sovereignty|Recognizes that data may be subject to laws associated with where it is stored or processed. Location and jurisdiction requirements should be checked for the actual service arrangement.
T|Geographic restriction|Limits access or processing based on allowed locations. It enforces a location-related policy; a geolocation signal alone does not establish a person's identity.
T|Regulated data|Data whose handling is constrained by applicable legal or regulatory requirements. Determine the obligation rather than assuming all government-related documents are automatically secret.
T|Integrity verification|Compares content against trustworthy reference evidence such as a digest or signature. Matching bytes can still contain malware; verification does not assess all security properties.
E|A payment service stores a token instead of a card number. The mapping vault holds the real number. The support screen masks what staff see, while TLS protects traffic to the service. These are tokenization, masking, and transit protection respectively. The correct choice depends on which step the question asks you to change.

P|Resilience keeps useful operations going; recovery restores them after disruption. Recovery Time Objective sets the target maximum restoration time. Recovery Point Objective sets acceptable data loss measured backward in time. Neither is the average repair time: Mean Time to Repair measures observed repair duration, while Mean Time Between Failures measures operating intervals between failures. Targets and measured performance are different kinds of information.
P|Backup, replication, and journaling solve different problems. A backup supplies a separate recovery copy; replication maintains another live copy but may replicate corruption or deletion. Journaling records intended changes so recovery can reconcile incomplete operations after interruption. Hot, warm, and cold sites differ in readiness. A tabletop discusses the plan; a failover test actually exercises switching. Successful backup jobs do not prove successful restoration.
F|Define critical service|Set time and data targets|Choose recovery resources|Test restoration and failover|Measure and improve
T|RTO|Recovery Time Objective: the target maximum time to restore a service. It guides recovery capacity and procedures, not how much data may be lost.
T|RPO|Recovery Point Objective: acceptable data loss measured in time. A 15-minute RPO requires recoverable data sufficiently recent to meet that target.
T|Hot site|A recovery environment maintained ready for rapid use with required resources and current-enough data. Readiness costs more and must be tested rather than assumed.
T|Warm site|A partially prepared recovery location with some resources available but additional installation, configuration, or data restoration required.
T|Cold site|A facility with basic space and utilities but limited operational equipment or current data. It typically requires more preparation before service restoration.
T|Immutable backup|A backup protected from modification or deletion during its defined retention period. It helps resist destructive changes but still needs restoration testing and protected administration.
T|Tabletop exercise|A discussion-based walkthrough of a hypothetical incident or recovery situation. It tests understanding and coordination without proving actual technical failover performance.
T|Failover test|An exercise that actually switches processing to alternate resources and validates service behavior. It provides evidence beyond discussion of the plan.
T|Load balancing|Distributes work among resources to manage capacity and potentially improve availability. Health checks and redundancy are still needed; distribution alone is not a backup.
T|Diverse power|Independent power paths reduce common failure exposure. Two devices fed by the same upstream source may still share a single point of failure.
T|Journaling|Records transaction intent or changes so a system can reconcile interrupted writes and recover a consistent state. It reduces corruption risk from incomplete operations rather than supplying an off-site copy.
T|Replication|Maintains copies of data on other systems to support availability or recovery. It may also reproduce mistakes, deletions, or corruption; it does not replace every backup requirement.
T|MTBF|Mean Time Between Failures measures average operating time between repairable-system failures. It is a reliability measure, not a restoration deadline.
T|MTTR|Mean Time to Repair measures average time to repair or restore a failed component or service in the stated context. It is observed performance rather than the business's target RTO.
T|Continuity of operations|Arranges continued delivery of essential business functions during disruption, including alternate procedures and resources. It can include manual work while technology is restored.
E|Order processing must resume within two hours and lose no more than ten minutes of transactions. Those are RTO and RPO respectively. A journal helps reconcile an interrupted write; a recent backup provides a recovery copy; replication may reduce outage duration. A manual order form supports continuity while technical recovery is underway. Choose the mechanism matching the precise failure and requirement.
